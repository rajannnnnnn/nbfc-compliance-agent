# ClauseCheck — Decision Record

Short ADRs for every non-obvious choice, per `CLAUDE.md` §5. Each entry resolves an item
raised in `docs/SPEC_QUERIES.md` before the code that depends on it was written — the
resolution was mine to make (the user asked for the recommended reading on every open item,
without further check-ins), and each is reversible if it turns out wrong.

Format: what was decided, what was rejected, why.

---

## ADR-001 — Real RBI corpus is user-supplied; the shipped corpus is placeholder text, shadow by construction

**Decided.** `app/corpus/corpus_sources.yaml` points at local files under
`data/raw/instruments/`. Those files do not exist in this repository. Until they do, `make
ingest` has nothing to ingest and the API runs with no active snapshot (`/readyz` reports
`CC-503-CORPUS-UNAVAILABLE`, per ADR-009). `data/raw/instruments/README.md` states the exact
filenames, format and the paragraph-numbering convention the parser expects.

To make the rest of the system demonstrable before those files arrive, `data/raw/instruments/`
also ships five **placeholder** text files, loudly marked at the top of every file:
`⚠ PLACEHOLDER TEXT — NOT OFFICIAL RBI TEXT`. Their numeric content (30-day release window,
₹5,000/day compensation, 08:00–19:00 contact window, 21-day/7-day cure notices, ₹250/hour
restoration compensation, six-month recording retention, one-day cooling-off, three-working-day
KFS validity) is drawn only from figures the product's own PRD and LLD already state as the
regulatory facts the rules must check — nothing invented beyond what the specification already
asserts. Everything else (surrounding sentence structure, non-numeric wording) is generic
placeholder prose, not a claim about what the RBI instrument says.

Every placeholder instrument is ingested with `verification_status: unverified`. Per LLD §11.2,
`shadow_if_unverified=True` makes every rule resting on it shadow automatically — it computes,
persists, and is measured, but never emits a citable finding. This is not a workaround; it is
the exact mechanism §11.2 specifies for this situation, load-bearing rather than incidental.

**Rejected: leaving the corpus empty until real documents arrive.** Would mean the demo, the
API, retrieval, the rule engine and the verdict validator have no data to run against, and the
user could not see the architecture work end to end.

**Rejected: fetching real RBI text now.** `rbi.org.in` returns 403 at this environment's proxy
(SQ-01), and the user asked to supply the documents directly.

**What changes when the user drops real files in:** replace the five files under
`data/raw/instruments/` (or point `corpus_sources.yaml` at real URLs and let `fetch.py` pull
them), set each instrument's `verification_status` in `corpus_sources.yaml` honestly (
`rbi_verified` only if hashed against a source you can name), run `make ingest`, and the same
rules go live without a code change — shadow mode lifts itself.

## ADR-002 — Corpus ingest reads local files by default; HTTP fetch is available, not required

Resolves SQ-01, SQ-02. `fetch.py` supports a `file://` scheme (or a bare path) alongside
`http(s)://`. `corpus_sources.yaml` for all five v1 instruments uses local paths. `source_url`
remains a required field for provenance, but when the URL is a local path, `fetch()` reads the
file and hashes it rather than opening a socket. `make corpus-verify` re-reads the same local
path and reports drift the same way it would for a remote source — useful the moment the user
edits a placeholder file, not only after a real network fetch.

## ADR-003 — `docs/CORPUS.md` reports placeholder status honestly, not resolved facts

Resolves M1-T10, M1-T11. `docs/CORPUS.md` is regenerated by `make ingest` and, for each
instrument, records verification status as `unverified (placeholder — awaiting user-supplied
source)` rather than promoting it. PRD §14 open questions 1–5 are recorded as **UNRESOLVED**
with "blocked on real source text", not answered from the placeholder. `CLAUDE.md` §8 is
explicit that a gap is filled with a recorded gap, never with something that sounds right.

## ADR-004 — Embedding dimension: 1536, not the LLD's literal 3072

Resolves SQ-04. `clause.embedding` is `vector(1536)`, indexed with HNSW. pgvector's HNSW
(and IVFFlat) index has a 2,000-dimension ceiling; `vector(3072)` cannot be indexed at all,
so the LLD's own DDL cannot run. 1536 is requested from the embedding API via its native
`dimensions` truncation parameter, keeping a real `vector` column (not `halfvec`) at full
index support. `CLAUDE.md` §3 requires the dimension come from config, never be hardcoded, so
the migration reads `Settings().embedding_dimension` at generation time rather than
literalising `1536` in DDL — a config change and a re-migration is how this gets revisited,
not a code edit.

**Rejected:** `halfvec(3072)` (half-precision, indexes to 4,000 dims) — correct but pays a
precision cost this corpus of a few hundred clauses does not need. **Rejected:** a different
embedding model — reopens a settled choice for no benefit at this scale.

## ADR-005 — `clause.applies_to_borrower_classes` added; the applicability filter gains a borrower-class predicate

Resolves SQ-13 — the blocking defect that would have made the PRD §11 temporal pair
unproducible. `entity_type` in the schema is the **lender's** class (`nbfc`); nothing filtered
on the **borrower's** class (general vs. microfinance), so the microfinance contact-hour clause
would pass every existing predicate and sit in `candidates` on a non-microfinance loan, free to
be cited decisively.

Added: `clause.applies_to_borrower_classes text[] NOT NULL DEFAULT '{}'` (empty = applies to
all borrower classes; a non-empty array is a positive restriction, e.g. `{microfinance}`).
`APPLICABILITY_SQL` gains
`AND (c.applies_to_borrower_classes = '{}' OR :borrower_class = ANY(c.applies_to_borrower_classes))`.
`retrieve_candidates` now takes `borrower_class: str` (`"microfinance"` when
`loan_account.is_microfinance`, else `"general"`), derived by the caller from the account row
— retrieval never queries `loan_account` itself, keeping the dependency rule in LLD §1 intact.
A clause excluded **only** by this predicate is retried without it for `context_only`, tagged
`reason="borrower_scope"`, joining the vocabulary LLD §8.5 step 7 already names.

Set at ingest by the parser recognising the microfinance conduct block heading (RBC2025 §H) and
tagging its clauses; everything else defaults to `{}`.

## ADR-006 — `is_whatif` added; `is_shadow` keeps a single meaning

Resolves SQ-19. Migration 0006 adds `assessment.is_whatif boolean NOT NULL DEFAULT false`.
`is_shadow` means only "this verdict's clause basis is unverified, do not count it as a
finding." A `POST /assess` with an `as_of` override sets `is_whatif=true` and leaves
`is_shadow` to reflect the instrument's real verification status. `loan_compliance_state`
recomputation excludes rows where `is_whatif` OR `is_shadow` is true; `include_shadow=false`
on the assessments endpoint filters `is_shadow` only, as documented.

## ADR-007 — Rule clause-excerpt access via a pre-resolved map, not a rule method

Resolves SQ-15. `Rule.evaluate` gains a fourth parameter:
`clause_excerpts: dict[str, str]` — clause_path → verbatim text, loaded once per assessment
by `verdict/assess.py` from the active snapshot for exactly the paths in `rule.clause_paths`,
before any rule runs. Rules stay pure, synchronous, and I/O-free; `facts.clause_excerpt(...)`
as written in LLD §11.3 is replaced by `clause_excerpts[path]` at each of its two call sites
(R01, R16).

## ADR-008 — `cc_app` grants via `ALTER DEFAULT PRIVILEGES`, applied after migrations

Resolves SQ-08. Bootstrap SQL creates the role and extensions only. Privilege grants
(`SELECT, INSERT, UPDATE` broadly; `DELETE` on `document`/`extracted_fact` only; no
`UPDATE`/`DELETE` on `audit_event`) move to the end of migration `0008`, once every table
exists, expressed as both an explicit grant on current tables and
`ALTER DEFAULT PRIVILEGES ... GRANT ...` so a future migration's new tables inherit the same
policy without a manual step.

## ADR-009 — Missing active snapshot demotes from a fatal boot assertion to a `/readyz` failure

Resolves SQ-09. Boot assertions that remain fatal: embedding dimension matches the live
column; every pinning path resolves (§2.3, unless `fail_boot_on_pinning_mismatch=false` in
`ci`); every non-shadow rule's clause paths resolve; `alembic current == heads`. "Exactly one
`corpus_snapshot` row has `is_active=true`" becomes a **non-fatal** check surfaced at
`/readyz` as `CC-503-CORPUS-UNAVAILABLE`, and the Celery task layer refuses to dequeue
`assess.*` work while it holds. This is required for ADR-001 to be observable at all: a fresh
clone with no corpus ingested yet must start, answer `/healthz`, and say clearly why it is not
ready, rather than crash-loop.

## ADR-010 — `check_key` stays the rule id across a rule's entire valid/NOT_APPLICABLE lifetime

Resolves SQ-17. When a field is covered by a rule (`rule.consumes` includes it), `check_key`
is always that rule's id, whether the rule fired or returned `NOT_APPLICABLE` and the model
decided instead. `'F:<field_key>'` is reserved for fields no registered rule covers at all.
This keeps one check's history addressable on one key across a commencement date (e.g. R16
before and after 2027-01-01), which is what `GET /v1/loans/{id}/assessments` and the portfolio
view need. `EV-TEMPORAL-001`/`-002` use `check_key="R16_contact_window"` for both dates, per
LLD §17.1 as written.

## ADR-011 — Context-only excerpts are validated exactly like decisive/supporting excerpts

Resolves SQ-18 — the guardrail hole. `validator.validate()` no longer `continue`s past the
`is_literal_substring` check for `role == "context_only"`. A context-only citation whose
excerpt is not a literal (whitespace-normalised) substring of the clause's `text` is rejected
with reason `excerpt_not_substring`, audited the same as any other rejection, and counted in
`cc_citation_rejected_total`. `hallucinated_citation_rate` (LLD §17.2) is computed over
persisted citations of every role, so the guarantee has to hold for every role. This is the
single highest-priority fix in the codebase, per `CLAUDE.md` §2.1.

`ClauseCandidateSet.by_path()`, called in LLD §10.2 but never defined in §4, is added: it
resolves a path across both `candidates` and `context_only`.

## ADR-012 — `context_only` re-query drops only the two date predicates; draft and citable stay enforced

Resolves SQ-12. LLD §8.5 step 7's "re-queried WITHOUT the date predicates" is implemented as
dropping exactly `effective_from`/`effective_to` on both clause and instrument, while keeping
`i.status <> 'draft'` and both `citable` predicates in force. A draft clause can never reach
`context_only`, matching `forbidden_citations` being asserted on every eval case, not only
adversarial ones (LLD §17.1), and PRD §10's requirement that the suite prove drafts are never
cited in a finding, in any role.

## ADR-014 — R16 reads the event timestamp in `Asia/Kolkata`; 19:00:00 exactly is compliant

Resolves SQ-16. `r16_contact_window.py` uses
`contact_datetime.astimezone(ZoneInfo("Asia/Kolkata")).time()`, not `.timetz()`, because a
`timestamptz` read back from the database arrives session-local (UTC by default), and using
its raw `tzinfo` silently shifts a 20:10 IST call to 14:40 and flips a violation to
compliant. The window stays inclusive on both ends (`WINDOW_OPEN <= t <= WINDOW_CLOSE`):
19:00:00 is read as the last permitted second, 19:00:01 the first violating one. This is a
judgement call flagged for correction once the real instrument text is available (SQ-16
remains open in `SPEC_QUERIES.md` for that reason) — it does not depend on ADR-001's
placeholder text and is worth re-checking against the real clause wording.

## ADR-016 — Field registry: 82 keys, the enumerated names taken as authoritative over the "61" prose

Resolves SQ-07. LLD §5.3's five group counts sum to 80 and its enumerated names count to 82;

## ADR-017 — Document text extraction runs synchronously in the API request; only `assess.*` is queued

Resolves SQ-23 — the missing route for document text between API and worker processes.
`POST /v1/loans/{id}/documents` calls `extract.service.extract_document(text=...)` in-process,
inside the request handler, persists facts and runs conflict detection synchronously, then
enqueues `assess.document(document_id, tenant_id, request_id)` — an id-only Celery payload, as
LLD §14 requires. Document text never crosses a queue boundary, never touches Redis, and is
never written to Postgres (facts and redacted spans are, per `CLAUDE.md` §2.3). The `extract.*`
Celery queue defined in LLD §14 is kept for a future async-extraction path (e.g. large PDFs
needing OCR) but is not on the critical path for v1; `extract_tasks.py` exists and is callable
but the API does not currently enqueue it.

**Rejected:** a short-TTL Redis key holding plaintext — narrows the "never in Redis" invariant
silently. **Rejected:** an internal callback endpoint — adds an auth surface for one process to
call back into itself for no benefit once extraction is synchronous.

**Cost:** request latency now includes Stage A. PRD §8.1's p95 target (<10s end-to-end per
document) is measured against this shape, not against a queued Stage A.

## ADR-018 — CI runs only rule-decided cases on pull requests; model-dependent suites run nightly

Resolves SQ-24. `numeric_rules` (fully rule-decided) runs on every PR. `temporal` cases split:
the sub-suite where a rule fires or returns `NOT_APPLICABLE` and the *rule's own* boundary is
being tested runs on PR; cases requiring the model's `no_clause_found` reasoning (the PRD §11
pair itself, and `abstention`) run nightly, where a provider key is provisioned once as a repo
secret rather than needed on every fork/PR run.

## ADR-020 — RRF weight raised to 2.5; the §8.4 "outranks" sentence corrected in code comments

Resolves SQ-10. At `k=60`, weight 2.0 makes a rank-1-pinned candidate exactly tie a candidate
ranked 1 in both vector and lexical lists (`2.0/61 == 1.0/61+1.0/61`), decided only by the
tie-break — not a genuine score margin as §8.4 claims. `rrf_weight_pinned` is set to `2.5` so
the intended precedence holds on score alone; the tie-break remains as the deterministic
fallback for genuine ties elsewhere.

## ADR-022 — `redact.py`'s pattern order: PHONE before ACCOUNT, not as literally listed in the LLD

The LLD's own prose (§13) says "ACCOUNT before PHONE would swallow ten-digit phone numbers,
so the list order above is normative" — but its literal list puts ACCOUNT (a 9-18 digit
pattern) ahead of PHONE anyway. Running the ordering test caught it immediately: a bare
10-digit mobile number matched ACCOUNT first, and the PHONE pattern had nothing left to match
by the time it ran, so every phone number was tagged ACCOUNT instead. Swapped so PHONE runs
before ACCOUNT, matching the stated intent rather than the literal list. `CLAUDE.md` §2 has
no non-negotiable this touches, so this is a plain bug fix, not a spec deviation needing a
sign-off — noted here only because it is the kind of thing that looks like a typo until you
actually run it, which is exactly why every module in this build was run for real rather than
only unit-tested against mocks.

## ADR-023 — extraction never persists `is_absent=false` with no typed value

Found by mypy, not by a test: `app/extract/service.py`'s per-field loop only set `is_absent =
True` when normalisation *raised*. A model response with `is_absent: false` and an empty or
whitespace-only `value_raw` fell through with `typed_value` still `None` while `is_absent`
stayed `False` — which would have violated `extracted_fact`'s own CHECK constraint
(`is_absent OR value_normalized IS NOT NULL`) at insert time, or worse, silently written a
`NULL` "present" fact if the constraint were ever loosened. Fixed by treating `typed_value is
None` as absent unconditionally, regardless of why it ended up `None`. `CLAUDE.md` §2.1's
citation guarantee and this fact-table invariant are the same kind of defect class: a
`None`/`False` combination that should be structurally impossible was reachable at runtime
and only mypy's strict optional-type checking surfaced it, which is the case for running
`mypy --strict` on every commit rather than treating it as a formality.

## ADR-024 — pinned clause lookups go through the applicability filter too

Found by the integration test that exercises the PRD §11 temporal pair against the real
ingested corpus, not by any unit test: LLD §8.5 step 2 reads "pinned = expand(pinning[field_key])"
with no applicability predicate attached, and I implemented it exactly that way at first.
The result: `contact_datetime`'s pin includes `RBC-AMD2026/p100W` (the amendment's own
contact-hour clause), so that clause showed up in `candidates` on 2026-09-03 — five months
before it commences — because nothing about being *pinned* checked whether the clause was
actually in force. Retrieving through the pin table bypassed the exact temporal check the
whole architecture exists to enforce, defeating the applicability filter for every pinned
field simultaneously.

Fixed by running `_PINNED_LOOKUP_SQL` through the same `APPLICABILITY_SQL` predicate as
vector and lexical search, and returning the full (unfiltered) expanded pin-path list
alongside the applicable subset so a pinned-but-excluded clause still seeds `context_only`
with the correct reason rather than disappearing silently. This is the same defect class as
SQ-13 (ADR-005): a mechanism that looks like a targeted shortcut (a hint table, a pin) quietly
carries no temporal or scope check unless one is added explicitly, and the LLD's own prose
never says to add it for the pinned path specifically. The integration test
(`tests/integration/retrieve/test_service.py`) now asserts both halves of the PRD §11 pair
and the microfinance borrower-scope case against the real placeholder corpus, which is what
caught this — a unit test with a hand-built `ClauseCandidateSet` would not have.
